按项目负责人的要求（2026-11-19），大约每工作 24 小时或每做完 3 批实验，用三个全新的子代理分别审计代码和仓库、研究方法、工作流程，

## 第 1 次（2026-11-19）

三个子代理互相独立，只给了要看的文件和会话记录，没有给结论。

### 一、研究方法

1. **脉冲在硬件上的好处目前有上限。** 只有读脉冲的 W_out 变成了加法（硬件网络约 2,830 万次乘加 → 约 117 万次加法），
   其余读实数总线的矩阵仍是稠密乘加。和它自己不发放脉冲的版本比，最多省约 1.5 倍。同等质量的 Transformer（约 34M，大部分是词表）
   每个 token 只要 1,100–3,000 万次乘加，硬件网络要 5,860 万次。`fpga_est.py` 只能估算脉冲网络，同一块 FPGA 上的
   Transformer 和线性注意力网络从没估算过；5.47 节自己也承认，质量相当的线性注意力网络放到 FPGA 上会比脉冲网络好。
2. **FPGA 的亮点还只是估算。** "单路快 14–17 倍"假设的是权重全部放在两块卡片上的设计，还没写出来；按已写好的内核（权重从外部存储读）
   估算，单路只比 GPU 快约 2.5 倍（`runs/g29_hw/fpga_est_u55cx1.json`）。GPU 那边还没测 8 位、4 位推理和融合内核。
3. **第三十八、三十九批的结论下得太早**：第三十九批是在第三十八批只有一个评估点时提交的，`g38_norm` 相对基准一直在变好却被写成"改变不大"。
4. **"梯子"有混杂因素**：网络大小、词的压缩编码（本身约 0.07–0.11）、只给脉冲网络的训练设置；各级的差加起来不会等于总差距。
5. **趋势目标做得少**：只有一个大小训了长训练；49 亿 token 以后换了老师（老师本身读了 98 亿 token）；没有按硬件代价的横轴。
6. **一些判断门槛和问题不匹配**，FineWeb 上没有换随机种子的重复实验，而有些决定依据的差只有 0.005–0.02。
7. **说法偏乐观**：零样本"和 GPT-2 124M 相当"只看了除 LAMBADA 外的五项；5.47 节的表混了平均和未平均的权重。
8. **被忽略的方向**：三值权重网络（同样能把乘法变加法，审稿人会问"为什么不用它"）、把总线也变成脉冲（唯一能让脉冲省下大量计算的路）、
   长文本（4–8k token）上的质量、FPGA 的 LUT 资源（脉冲驱动的加法可以放在那里）。

### 二、代码和仓库

- 三个新功能（`spike_soft`、`bus_norm`、`--mlp spike|lif`）计算正确。唯一真正的错误：`--mem_kind gla` 不能在两次调用之间带状态，
  长文本评测、逐 token 的评测、`hw_cost.py` 遇到它都会出错（训练不受影响）。
- `sample.py` 对 FineWeb 的模型一直用错分词器（样例是乱码，不影响任何评测数字）。
- 带可塑突触的网络，训练脚本一直跳过了低精度模拟（判断条件过时，5.44 节起已经支持）；`slurm/hw.sbatch` 反过来没排除不支持的选项。
- `hw_cost.py` 不认识线性注意力（把它当成会增长的 KV 缓存算），也没有拒绝 `spike_soft`；`eval_long.py` 对线性注意力也要求滑动窗口。
- 多处文档过时："最新结论在 5.28–5.30 节""进行中的实验在 5.24 节"、`runs/README.md` 只列到 g17、"可塑突触是唯一偏离"、
  已删除选项的提交号不全、`docs/running.md` 漏了几个选项、CLAUDE.md 里的分支规则。

### 三、工作流程

1. 上下文被压缩以后，教训没有留下来，同样的失败重复出现（定时唤醒不能用、提醒被 30 分钟的默认时限停掉）。
2. 不少给负责人的回复是英文的（11-16、11-17 两天大部分是）。
3. 早期结果被当成结论说出来，后来又收回（换老师、"差距固定"等）。2026-11-19 回答愿景时说"差距一直在 0.26、增长速度和 Transformer 一样"，
   和自己的数据不符：同一个老师下差距随数据变大（0.231 → 0.267 → 0.298）。
4. 请负责人动手之前没有先确认可行（VPN 登录两次后才发现网关不通）。
5. 负责人不在时汇报太多、太碎，又夹杂运行编号和术语；负责人回来仍要问"整体情况"。
6. 提交太频繁（"不要滥用提交"之后频率几乎没变）。
7. 集群会话不出声时，本会话也跟着不出声（`g35_mspk` 晚了约 2 小时才去问）。
8. 可避免的启动问题浪费了算力（第五千步评估时显存不够、基准脚本失败两次、空闲的卡位约 25%）。
保持下去的：讲解清楚、如实更正、根因分析、删除前逐项确认、给集群的指令清楚、决策规则写在结果之前。
